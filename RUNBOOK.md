# RUNBOOK: operating the facilitator board

For an agent sitting behind the board. Read this cold and start; nothing else is assumed.

The tool: `server.py` (Python) serves `index.html` (vanilla JS) at http://127.0.0.1:<port>, where the port is the `port` in `run.config.json`: 8877 on a new install where it is free, and another one once `facilitator run` has had to move the board (see "Bringing everything up"). Its packages go in the standard `.venv` beside it, each locked to an exact version and checked against a fingerprint. For a new checkout run `./install.sh`, which prints one short numbered section at a time and asks only about the phone client. First it needs Claude Code or Codex (`claude` or `codex` on PATH, either one); with neither it prints the official links, asks you to run `./install.sh` again once one is installed, and stops with nothing changed. Then it needs Chrome, which it asks macOS about (Spotlight first, then Launch Services) without reading the Applications folder, because the board is meant to run as its own Chrome app window and not in a browser tab; without Chrome it prints the download link and stops the same way. Then it builds the private environment and never changes your own Python: it finds or installs uv (with Homebrew, or the astral.sh installer for one exact uv release, 0.12.22, which is downloaded first, checked against the fingerprint kept in the `facilitator` file and run only when they match, and told to leave shell profiles alone; it has to be uv 0.9.0 or newer, the first that installs Python 3.14, and an older one stops the run with one line saying to upgrade it), runs the setup on the `python3` on PATH when that is 3.9 or newer (the one macOS ships is enough) and otherwise on a Python 3.14 that uv installs for itself, then builds the `.venv` on a Python 3.14 that uv installs and manages itself, whatever runs the setup, so every checkout runs the Python the board is tested on (a `.venv` that is missing, broken or on another Python is built again, a board running on the old one is stopped first, and uv's Python 3.14 needs macOS 11 or later), syncs the packages from `requirements.txt`, which names every one with its exact version and fingerprint and is installed with `--require-hashes`, so a package that differs is refused, writes `run.config.json` and `seed.json` from the examples when they are missing (a new `run.config.json` names port 8877 when 8877 and 8878 are free, and otherwise the next free pair above them, with a line saying which; the examples hold no lane and no card, a white background and a full-screen window, so a new install's first board opens full screen, white, on the home page, with no tab and no example project, and a file that exists is never rewritten; see "Bringing everything up", "The settings page", "The home page" and "Seeding a board"), and leaves out the packages only the tests need: `./install.sh --dev` adds them, needs node and npm, and installs them into `tests/node_modules` from `tests/package-lock.json` with `npm ci` and without running any package's scripts. In an interactive terminal it then asks "Would you like to use the phone client?" (a single key, y or n); on no it goes straight on. On yes, 4.1 says that Tailscale connects the phone to the board on the Mac privately, without opening it to the internet, and is free, and asks whether it is installed on both devices; if not, it asks whether to install it now or later: now prints the Tailscale download link, points to the App Store for the phone and waits for a key, and later prints a short reminder that the phone client needs Tailscale with HTTPS certificates switched on, and skips the next question. Otherwise it asks whether HTTPS certificates are switched on for the Tailscale account, and on no or not knowing prints where to switch them on (Tailscale -> Network -> DNS -> Enable MagicDNS and allow HTTPS Certificates). Then 4.2 prompts for the app password, keeping one that is already set. Last it registers the `facilitator` command and the shared agent skill under a single check-mark line and prints the next steps. It adds nothing to Claude Code's settings and no longer asks about Claude limits. A run with no terminal skips every question, treats the phone client as no and says so in one line, so it finishes without a password; run `facilitator password set` before enabling the bridge. That command, like the installer's password step, runs on the `.venv`'s Python, since the `python3` macOS ships cannot make the password's `scrypt` hash; with no working `.venv` it says to run `./install.sh` first. It is safe to run again, and after requirements change it syncs the `.venv` on its own. `facilitator uninstall` (or `./uninstall.sh`) removes only setup artifacts recorded as installer-owned, including its agent-skill links and, where an older install added one, the status line entry: a wrapped status line is put back as it was, a settings file that install made is removed once it is empty, and an entry changed by hand since is left alone with a line saying so; it preserves preexisting or edited config and always keeps board data and bridge credentials. Right after its banner it asks whether to keep the card attachments (`../facilitator-internal/uploads/` and the older in-repo `uploads/`); Enter, an unclear answer or a run with no terminal keeps them, only a clear no removes those two folders (a link is kept, never followed), and `--keep-attachments` or `--remove-attachments` answers without asking. The `../facilitator-internal/uploads/` folder is also read by every other copy of the board beside this one, so when other copies exist a clear no is followed by a second question naming them: that folder stays unless the second answer is a clear yes, and neither flag nor a missing terminal answers for the other copies. Uninstall has no dry run. Artifacts from the former `facilitator install` have no ownership record, so uninstall keeps those legacy files for manual inspection. `facilitator run` starts the server with that `.venv`. The server needs Python 3.11 or newer and refuses, in one sentence, to start on anything older. Stacked discussion boxes, one per point, each a mini-thread between the owner and one agent. Messages queue FIFO into the agent's terminal session; every message and reply persists (`state.json`, `transcript.jsonl`, both written beside the server, both gitignored). The endpoint reference is the module docstring in `server.py`; keep it truthful as endpoints change.

## The loop

From the agent conversation that owns your lane, repeat the current two-call production protocol. The installed `facilitator` skill resolves the lane and its `scripts/onboard.py wait` helper makes both calls for each claim. In every command here, `$PORT` is the board's port: the `port` that `scripts/onboard.py inspect` reports, which is the `port` in `run.config.json` (8877 unless `facilitator run` has moved the board to another pair). Read it fresh rather than remembering it, since a board that moved stays on its new port, and set it once in your shell (`PORT=8877`, say) or write the number in:

    curl --max-time 60 -sS "http://127.0.0.1:$PORT/wait?owner=facilitator&timeout=50&agent=claude"
    curl -sS -X POST "http://127.0.0.1:$PORT/ack?owner=facilitator&token=<the ack field>"

`agent=` states your name; the board's card rows show each lane's live agent name, or offline, from exactly this. It returns `{"box": id, "title": ..., "messages": [...], "queued_after": n, "ack": token}` on a claim, or `{"idle": true}` on timeout.

The `ack` token is the receipt for the card you were just handed, and confirming it is part of claiming, not an extra. A hand-off is provisional until you confirm it, because the answer can die on the wire: your own kill timer fires, the connection drops, and the server thinks it delivered a card nobody ever saw. Confirm it the moment the claim lands, before you start reading or working. A card nobody confirms goes back to the front of its lane's queue after 90 seconds and its colour falls back to the queued grey, so nothing sits green with nobody on it. Confirming twice is fine; the second call answers the same `{"ok": true}`.

WARNING: a loop without the confirm line claims cards it cannot keep. Every claim bounces back to the queue 90 seconds later and gets handed out again, forever, and your reply lands on a card you no longer hold.

After reading the separate `/fresh` result as described below, answer with a complete reply:

    curl -sS -X POST --data-binary @reply.txt "http://127.0.0.1:$PORT/reply?box=ID"

`ctx=` is optional compatibility data. A supplied context is stored and must be at most 50 words. The server accepts a reply without one.

- `/wait?owner=...` claims the oldest queued box in your owner lane and marks it busy. Never leave a claim unanswered; an open claim blocks your whole lane (each owner has its own busy slot, see Owner routing below).
- Immediately before **every** `/reply`, including an interim or worker-completion reply, call `GET /fresh?owner=YOURLANE` and read its result before composing and sending. If it returns messages for the card you are answering, include them; those messages are folded into the held claim. If it names a different held card, handle that claim first and do not use its messages in a reply on another card. With no held card, `/fresh` returns an empty message list and hands over nothing; queued messages on other cards remain for their own claims. Do not combine a `/fresh` call with a prewritten reply in one command.
- Three nets sit under a claim, in order: a hand-off written into a dead socket rolls back at once, an unconfirmed claim returns after 90 seconds, and a claim older than 15 minutes is stolen back. Do not lean on any of them; confirm what you claim and answer what you confirm.
- Before going idle, check whether anything is waiting on your lane: `GET /unread?owner=YOURLANE` answers `{"queued": N, "claimed": M}`, messages still waiting plus messages in the claim you hold. It reads only, so it is safe from a hook. Paste this as a Stop hook command and go back to the loop instead of idling whenever `queued` is above zero:

      curl -s "http://127.0.0.1:$PORT/unread?owner=facilitator"

## Replies

- 100 to 150 words or fewer. Plain conversational tone: no coined shorthand, no unexplained jargon; a term either gets defined by what it concretely does or gets dropped. Paragraph breaks and short lists over walls of text. Depth comes from choosing what to say, not from length.
- No em dashes, in titles or in replies. Banned.
- Every reply fully self-contained. The box shows ONLY the latest reply, so a short follow-up ERASES a longer answer. Restate rather than reference.
- A small-card version, when needed, is a separate urlencoded `short` query on `/reply`. If it is omitted, both cards show the full body. Never put `---` in the body as a hidden separator. It is authored Markdown and renders as a horizontal rule.
- Answer what was asked and stop: no unsolicited offers, no "want me to" tails, no validation preambles.
- `POST /note?box=ID` consumes and releases a held claim. Do not use it for progress on a claim: later owner messages can be hidden until a full reply. For work that continues, register `/working`, keep its heartbeat current, and send a full `/reply` with the flag still live. That reply remains deferred until the work truly ends and the flag drops. The removed `quiet` query is rejected.
- The colour law is the machine's now, not your discipline: every card sits in one server-side state and the colour is a pure read of it. A normal reply under a live working flag lands the card in deferred, still green; the turn is handed over when the flag drops (`/working?box=ID&v=0`) or its heartbeat expires. A progress note stays in note until another event or the heartbeat ends.
- `POST /testing?box=ID&v=1` raises the ready-to-test marker: use it only once a delivered change is actually available for the reader to try, not because a merge is planned or a reply reads as finished. It is refused unless the card is awaiting the reader (a completed reply waits and no job runs), so it never marks active, queued or done work. `v=0` lowers it by hand; the reader answering the card, and close/done, lower it on their own. It only sets the flag: no reply, no claim, no move.
- A reply that closes or parks a box carries zero new information. Folded boxes go unread. Keep-in-mind notes go to an open box or the project docs.

## Titles

A user-created box is auto-named with the chopped first line of its first message, which reads badly. When you claim such a box (title ends in "…" or just parrots the message), set a brief accurate title as part of answering it: `POST /title?box=ID`, raw text body. Keep titles short enough to sit on one line.

## Status changes

- Only the owner closes. The agent flags duplicates and proposes merges; green comes from the owner's hand or their explicit word. A box was once closed by the agent mid-use and had to be reopened; do not repeat that.
- "TBDL" from the owner means: park that box to Later AND record the deferred work in the relevant project doc.

## Context strips

`POST /context?box=ID` stores optional historical context (50 words max, refused over that, never truncated). `/reply` no longer requires `ctx=`. When answering, use the current claim and `/fresh` for new messages rather than relying on an old strip.

## Permission blocks

Follow the current host's permission rules and the user's authorization in this session. A board card does not override a host restriction. If a step is blocked, complete permitted work, explain the blocked step and reason in the relevant reply, and keep the listener running when possible. Do not infer permission for pushes or destructive operations merely from these operating instructions.

## Restarts

- A restart re-queues claimed-but-unanswered messages. Expect duplicate deliveries; answer "already handled, restart re-queue".
- A stop is graceful: open requests get three seconds to finish and a listener waiting on `/wait` is answered `{"idle": true}` at once, so the loop simply asks again.
- `facilitator stop` ends the board and closes its window. It finds the server the way `facilitator restart` does (the one process listening on the configured port, read back as this folder's `server.py`), sends it one SIGTERM, and says `Board stopped.` only once that process is gone and both the board's port and the phone's port above it can be bound. It edits no file in the board folder; the save on the way out is the server's own. A server still there after ten seconds is left alone, nothing is closed, and the command exits 1 naming `--force`. `facilitator stop --force` reads the process a third time and, only if it is still the same one, ends it outright with one SIGKILL to that pid. That skips the graceful stop: a request in flight is cut and no stop line reaches the log, though every saved change is already on disk, since saves are atomic. After the server is gone (or when it was not running) the command closes, by window id, only a Chrome window whose every tab is the board's own page, either the address `app_url` names or the configured port on a loopback address, and reads that window again just before closing it. A board tab in a window with other tabs is left open and one line says so. It never starts Chrome, and when Chrome cannot be asked it says so in one line. On a checkout with a phone password (`facilitator password set`), the last thing it does, once the server is confirmed gone (or when it was not running, which still takes a link that points at this board off), is take the phone link off through the same code and checks as `facilitator bridge off`: only this board's own root handler goes, and every other Serve path, port, Funnel route and Service stays. It says nothing when that works or when the link was already off, and one plain line (`The phone link could not be taken off (<why>). Run facilitator bridge off when that is fixed.`) when it cannot, Tailscale not answering for one; that never changes whether the board stopped or the exit code. A stop that leaves the server running (the ten second case) leaves the link as it is and asks Tailscale nothing. A checkout with no password changes no rule: it keeps the one line saying a phone bridge is active, when one is and a server was stopped. `--dry-run` prints the plan and signals and closes nothing, and names the bridge step when a password is set. A stop that lands while `facilitator run` is still starting the server finds nothing on the port, says `Board was not running.`, and the board then comes up; restart has the same gap, so do not run them at the same time.

## The log

Three dated files in `facilitator-internal/logs`, the sibling folder beside this repo, so nothing here is ever committed:

- `server-YYYYMMDD.log`: what the board did. Start and stop with the reason it stopped, every refusal it sent, every push outcome with the service's own words, every change to the stored push subscriptions, board events, unusually slow phone command/state requests, a save that failed, and every crash.
- `client-YYYYMMDD.jsonl`: what the three pages reported: a thrown error, a rejected promise, a request that failed, a card that would not draw, a timer that ran more than two seconds late, a saved phone incident history, and what the phone's notifications did. Every line carries `client`, the kind of window that sent it (`chrome`, `electron`, `tauri`, `safari`, `phone` or `other`, worked out by the page from its user agent, which is never sent or stored), and `window`, 16 random hex characters made once per page load (the phone's incident `session` is the same id). The route refuses any other value, and a page loaded before the server was updated sends neither until it is reloaded.
- `bridge-YYYYMMDD.log`: the tailnet share going up and coming down, and what ended it.

Each file caps at 5 MB and rolls, thirty of each kind are kept and older ones are deleted, so the folder cannot pass about 150 MB whatever goes wrong. One line is one event, as JSON:

    {"ts": "2026-09-03T18:22:41.108Z", "level": "info", "kind": "refusal", "box": "m12", "route": "/reply", "code": 400, "reason": "bad box"}

Three levels and no more. INFO is what happened and is on by default; ERROR is something that failed and was not meant to; DEBUG is the noise you switch on while hunting, a line per request with its milliseconds plus claims, acks and unconfirmed hand-offs. Raise it for one run and no longer:

    FACILITATOR_LOG_LEVEL=debug .venv/bin/python3 server.py

`log_level` in `run.config.json` (`info`, `debug`, `error`) sets the standing level and that variable beats it; a level nobody has heard of falls back to `info` rather than stopping the board. `FACILITATOR_LOG_DIR` moves the whole folder, which is what the tests use so no test can write into the real one. `GET /log?lines=N` tails the day's server file.

Phone diagnostic history is off by default: tap the version on Home seven times, less than a second apart, to turn developer mode on and show Diagnostics, enable Control + Shift + M, and allow automatic saves. Seven more taps turn it off and discard unsaved history in the open page; the switch is kept in that phone’s local storage, while page errors and notification logs stay on.

With developer mode on, the phone keeps a sparse 120-second lead-up to a glitch in page memory, then records up to 20 seconds of recovery before uploading one incident. Edge pulls, card selection, and vertical response scrolling retain coarse input and frame timing; ordinary successful state polls are summarized every ten seconds so they cannot crowd out gestures. Frames are watched only for 5 seconds after a touch, a key or a new board reading, so a page with nothing going on asks for none; the 100 ms timer runs all the time and still records every stall. Schema 4 also records bounded Enter-event, viewport, and handler decisions without draft text. Schema 5 adds where the response stood during a swipe on it, described below. A visible UI span of at least 150 ms, request of at least two seconds, failed operation/request, page problem, visible frame/timer gap, broken render invariant, or a response swipe that moved nothing may save automatically, with a 30-second automatic cooldown. The Save diagnostic history button in the Diagnostics section of the phone's settings drawer, or Control + Shift + M, records the same bounded history and shows that it is collecting for 20 seconds; it says saved only after the server confirms the write. A press made while an automatic save is still recording or sending is never refused: it takes its own marker and its own 20 seconds at once, and goes out right after the automatic one. A save batch stays capped at 12 KB on the phone and the route refuses any body over 16 KB. The phone still makes at most four save attempts per minute, including each compatibility POST, and the server permits four incident writes per minute across all pages and reasons. Failed and offline manual saves retain their original marker in that open page for an explicit retry. A page hidden during collection can send a best-effort beacon but cannot confirm persistence; closing the page loses history that was never sent. A schema-3 receiver still accepts ordinary 120-second lead-up and 20-second recovery histories; Enter details are omitted, and a save that missed them says the server needs updating. A stale schema-4 report rejected by that receiver gets a budgeted schema-3 retry. A schema-4 receiver gets schema-5 histories with the new gesture fields and parts left out and a cancelled touch sent as `touch-end`, the same way and within the same budget; a manual save that lost them says the server needs updating. Schema-1/2 receivers use the older 40-event/60-second format.

Schema 6 adds a short `timing` record for keyboard scrolling in the reply or drawer list. It holds each step's computed time and set position, the offered frame time and callback time, start and end times for board handling, JSON parsing, list and reply drawing and glass pick measuring, and any supported long tasks. Frames are watched for the whole hold. Times are milliseconds from the save marker; positions are CSS pixels. Control + Shift + M saves it, and gaps of at least 100 ms between steps or frame callbacks mark a `slow-ui` save with the same recovery time, cooldown and caps. Late steps point to busy page work; jobs that overlap are suspects. Timely steps with late frame callbacks point toward drawing work such as blur. Both on time point toward the recording. A frame callback offers a chance to draw, not proof the pixels appeared, so the last two cases may need a camera check. The buffer holds at most 240 rows, saves at most 6 KB within the 12 KB batch, and counts dropped rows in `timing.lost`. There are no extra layout reads per step, text, key values or addresses. Older receivers get ordinary history, and a manual save that lost timing says the server needs updating.

On schema 5 a touch that begins on the selected card's response also records the response's scroll position (`top`), how far it can scroll (`range`), its visible height (`view`), which edge it is at (`edge`: `top`, `bottom`, `middle`, or `none` when it cannot scroll), whether an older reply is showing (`hist`), keyboard and focus (`kb`, `focus`), and how late the page handled the touch (`lag`). The intent adds the finger's direction (`dir`, `up` or `down`), whether it has gone 24 px (`far`), `edge` and `lag`. The first scroll event adds `wait`, the time from the touch to that scroll. The touch end adds how far the position moved (`moved`), how many scroll events arrived (`count`), how long the touch lasted (`ms`), whether the same response is still on the page and selected (`same`), and whether page script cancelled the pan (`prevented`); a touch the system cancelled ends as `touch-cancel`. A `taken` input names what took the touch instead (`by`): the drawer pull, the card swipe, a focus change, the shade over the page, the startup curtain, or a menu still sliding away. A `reply-swap` phase means a render replaced the reply's words while the finger was down or within a second after. Scroll position and heights are read only at touch start, intent and touch end, and no coordinates are ever recorded, only the direction. An intent with no `edge` began off the response, on the title or the typing row.

That same history is saved automatically as `no-scroll` when a swipe on a response that can scroll moved nothing. It is judged at touch end, or 300 ms after the intent if the finger is still down: no scroll event arrived, the position did not change, the finger went at least 24 px, and it was not pushing into the edge the response was already at. The 300 ms and 24 px are not yet checked on the phone. The save shares the 30-second cooldown and the four-per-minute cap, each card saves at most once every 120 seconds however often it stays stuck, and it only runs once the server offers schema 5. A `no-scroll` save has no schema-4 form, so a receiver rolled back under the open page leaves it held there rather than saved under another reason.

An incident's HTML build token names only the loaded phone page; its worker field names the cache version reported by the controlling worker, or `unknown`. Neither is a hash of every loaded asset. Frame callbacks show frame opportunities, not proof that pixels appeared. A late timer after a page resumes is not treated as a continuously visible freeze. Browser/OS causes still need an affected-device capture when these phase timings do not settle them.

Why a phone stops getting notifications is followed through these lines. The server writes one INFO line for every change to the stored subscriptions, each with `count`, the number stored after it, and `rec`, the first eight hex characters of a SHA-256 of the endpoint, which is the same for the same endpoint and cannot be turned back into it. `pushsub` is a phone subscribing (`action` is `new` or `replaced`, and `session` says whether a live sign-in was stored with it). `pushunsub` is a removal the phone asked for (`removed` is false when nothing matched). `pushgone` is a subscription dropped because the push service answered 404 or 410 (with its `status`). `pushsession` is a subscription skipped for one turn because its sign-in has ended (`reason` is `no live session`); nothing removes such a subscription, so it is skipped again until the phone unsubscribes or the service reports it gone. The `push` and `pushfail` lines carry the same `rec`. The phone writes three kinds into the client file, each made of fixed words, flags and bounded numbers, never text. `pushreceived` is one push that reached its worker: `outcome` (`shown` or `skipped`), for a skip the `reason` (`show-failed`), `ms` (how long the display attempt took), `status` (0 because display no longer asks the board first; older workers recorded the sign-in check's time, HTTP status and failure reason), `n` (the worker's own record number), `worker` (its cache version) and `at` (when the push arrived; the phone sends how long ago and the server works out the time). `notifycheck` is written each time the app starts or comes back (`source` is `start` or `return`, and a return is recorded at most once in ten seconds) with `perm` (`granted`, `denied`, `default` or `unsupported`), `reg` (whether the worker is registered) and `sub` (`yes`, `no` or `error`: whether a push subscription exists, never its address). `notifylost` is its own line, written beside `notifycheck`, when `perm` is `granted` and `sub` is `no`. The worker keeps its records in its own database (the newest 50), sends them oldest first and 20 to a request when the app opens or after a push it showed, and removes a record only once the board has taken it, so a phone that was out of reach reports its earlier pushes when it can. The route refuses any other kind, field or value with a 400 and takes 60 `pushreceived` lines a minute where the other kinds take 10. A server not yet restarted onto this code refuses these kinds: the worker keeps its records and the page drops its notices.

What becomes of a tap on a notification is followed through four more kinds in the client file, tied by one `tap` id: eight random hex characters the worker makes at the tap and hands to the page in its message and in the address it opens (`/m?box=...&tap=...`). A page opened by an address with no `tap`, as by an older worker, writes `none`. Every value is a fixed word, `yes` or `no`, a bounded number, the card's id (the line's own `box`, left out when the id is not a card's) or the tap id, never message text, a title, a key or an address. `notifytapready` is the worker's early record, with `stage` `received` as soon as the click handler starts and `stage` `ready` after it lists the windows, before it tries to focus one or open a new one. Both carry the original click time as `at` (Unix milliseconds, unchanged if sent later) and `worker` (the cache build, `facilitator-m-9` for this change). Only `ready` carries `windows` (the number of controlled /m windows, capped at 1000), `visibility` (`visible` or `hidden`) and `focused` (`yes` or `no`) for the first /m window the routing loop will try, sampled before focus. With no app window, `windows` is 0 and both state words are `none`. The `received` stage leaves these fields out because the window list is not known yet. Each write starts in the worker's existing database and has its own event lifetime; routing waits for neither storage nor upload. `notifytap` is the worker's final line, written once the tap has been acted on: `windows` (how many of its /m windows it found), `route` (`message` when it posted to a window, `open` when it asked for a new one, `failed` when it could not list its windows), `focus` (`ok`, `rejected`, or `none` when no window was tried), `opened` (on `open` only: `client` when a window came back, `null` when none did, `rejected` when the open threw), `ms` (the tap to the post, or to the open's answer) and `age` (seconds since the notification was shown, left out when the worker cannot tell). `notifyarrive` is the page's line when the card reaches it: `via` (`message` or `url`), `yes` or `no` for `reading` (the page holds a reading of the board), `found` (that reading has the card), `visible`, `home` (the all-projects view is open) and `hist` (an older reply is showing), and `menu`, what is open over the card (`cards`, `settings`, `projects` or `none`). `notifyresult` is the page's line once the card is the selected one and drawn, or two seconds after it arrived: `shown` (the card is the selected one), `covered` (the same words as `menu`, at that moment) and `pending` (the page is still waiting for a reading that has the card). To read one tap, follow its id: `shown` `yes` with `covered` `cards` is the right card under an open card list; `pending` `yes` is a card the phone had not read yet; a `notifytap` with `route` `message` and no `notifyarrive` has no recorded page receipt, since posting has no acknowledgement and page logging can fail. A `received` without `ready` narrows the gap to window lookup; a `ready` without `notifytap` narrows it to routing after lookup. Neither proves a stall, since later logging can also fail. The early record describes the first chosen window, even if a failed post later makes routing try another. No line can prove a click the operating system never dispatched, and storage failure, queue eviction, an old worker or rate limiting can also leave gaps. The line's `ts` dates its upload; the early record's `at` retains the click time. The route takes 10 of each of these kinds a minute, with the two `notifytapready` stages sharing that kind's cap. It refuses any other field or value with a 400. None of this changes where a tap goes. The address keeps its `?box=` and `&tap=`, so a page reloaded at it writes its `url` arrival again with the same tap id; a second `via` `url` line under one id is that reload, not a second tap. A server not yet restarted onto this code refuses these kinds, so the worker keeps its lines and the page drops its own; the phone app has to be reopened to load the worker and page that write them.

`/send`, `/create`, and `/m/state` responses carry a numeric server-duration header for the phone history. A request on one of those routes that takes at least one second also writes one rate-limited `slowrequest` INFO line. These timings cover server handling, not the phone's network transit.

A phone-bridge request the sign-in gate turns away, for lack of a valid session or as a cross-site GET (see the cookie note under the bridge command), writes one `signinrefused` INFO line with: `method`; `route` without its query (a file under `/uploads/` or `/laneimg/` shows as `/uploads/*` or `/laneimg/*`); `cookie_header`, whether a Cookie header came; `cookies`, how many it held; `session_cookie`, whether one of them had the session cookie's name; `session_known`, false for a request with no valid session and true for a cross-site GET, which carried one; `reason`, `cross-site-get` on a refused cross-site GET and left out on the others; `sec_fetch_site`, `sec_fetch_mode` and `sec_fetch_dest`, each `absent` when the browser sent none; and `client`, the same classes as the client log, worked out from the user agent, which is never stored (an iPad that asks for the desktop page reads as `safari`). It is rate limited to one line per route and reason every five seconds, and the first line of the next window carries `folded`, the number turned away in between and left out. It never holds a cookie value, a query, a user agent or an address, and writing it changes nothing about the answer.

The dated file is the only stream. Started by the CLI the server's output goes nowhere else, so no event is written twice; started by hand in a terminal, INFO is mirrored there as well in a short human form, so it says what it is doing as it does it. A crash lands in the file like anything else: a request that throws, and a start that dies of something rather than being asked to stop, each write one `crash` line naming the exception's type, its own words when those words are plain enough to keep, and where it happened as `file:function:line` with no path in it. A fatal one is followed by the stop line that says which type ended the run. The one failure no file can hold is a server that dies before its logger exists, which is an import going wrong; `facilitator run` notices the child is already gone and says so in one sentence, and running `.venv/bin/python3 server.py` by hand shows it.

Five things never appear in any line: message or title text, keys and authentication tokens, whole push endpoints (the service's host only, plus an eight character hash to tell one subscription from another), file paths, and email addresses. The rule is kept where the line is written, by not passing those things in: the board event line carries a message's length and never the message, and the lane-creation line carries the folder's name and never the path to it. Phone incident entries accept only fixed event/state names, bounded numbers, existing card IDs, and canonical operation receipt IDs. Anyone adding a line keeps it that way. A filter over a formatted line can be fooled; not passing the text cannot.

## Real work

Real work ships from boxes: delegate bounded builds and scans when delegation is available and authorized, and report results in the ordering box. Follow the actual session's authorization for pushes and destructive operations. After work is finished and verified, stage and commit its changes when authorized.

## Delegation

The listener normally delegates substantive bounded work and stays responsible for the card, unless the owner asks it to do the work directly or the current host does not authorize delegation. Sort by the shape of the job before starting; a misjudged job need not be handed off halfway through.

Every worker brief carries six parts: the goal as one checkable sentence; full context, since the worker starts knowing nothing; boundaries, what it must not touch and which neighboring work is someone else's; the output contract, the exact shape coming back; proof, the worker verifies its own work (driven browser or equivalent) before reporting; and the house rules (plain words, no em dashes, no signatures, never restart the server, delete any probe box after use). Quality test: a stranger with no history could do the job right from the brief alone.

Any work belonging to a card carries that card's green flag for exactly as long as it is happening: worker runs, but also verifying a worker's result, post-build checks, and committing that card's code after the claim is released. `POST /working?box=ID&v=1` before starting, `v=0` the moment the card's work truly ends. Green means exactly the machine's two green states: working (claimed right now, or that card's work happening anywhere) and deferred (the same, with a reply already waiting to become the owner's turn when the work ends).

Green is verified, not trusted: registration starts a heartbeat clock, and without `POST /ping?box=ID` at least every 75 seconds the green expires on its own, so a dead job can never leave a card stuck green. Keep a pinger beside any long job:

    ( while curl -s -o /dev/null -X POST "http://127.0.0.1:$PORT/ping?box=ID"; do sleep 30; done ) &

and kill it when the work ends. The server also watches the other direction: an agent alive but absent from the listening call for over a minute, holding no claim and no live job, makes the bar read "working, card not marked". Do not let that be true of you.

## Who can reach the board

The board's own port refuses a request that another website sets off, with a 403 and one log line per route per five seconds that carries nothing the request held. It checks three things: the `Host` must be `127.0.0.1` or `localhost` on the board's own port, an `Origin` header must name that same address, and a `Sec-Fetch-Site` header, when the browser sends one, must say same-origin or none. The board's own pages, the Mac app window, `curl` and `scripts/onboard.py` send no `Origin` and no `Sec-Fetch-Site`, so they are untouched, and every route in the loop above works as before. The one thing another site may do is open `/` or `/m` as a page, because that is how the Spotify sign-in comes back; the page is read and nothing is changed by it. The phone port and requests Tailscale forwards go through the bridge's own gate instead, which this does not change. A browser too old to send `Sec-Fetch-Site` is held only by the `Host` and `Origin` checks, which miss a plain cross-site read that carries no `Origin`.

Every answer from either port carries `X-Frame-Options: DENY` and a `frame-ancestors 'none'` policy, except a successful `/m` page served directly on the local board port: that page carries `SAMEORIGIN` and `frame-ancestors 'self'` so the Mac board can show the real phone page in its narrow view. The phone port, forwarded bridge requests, refusals and the Mac root retain the full framing ban. Another site cannot frame the phone page or wrap its Mac parent. An answer that already carries a policy (an upload's sandbox) keeps it. A panel picture (`/laneimg/`) is served the way an upload is: `nosniff` and a sandbox policy, so even an SVG runs no script.

The files the board keeps about its owner's work (`state.json` and its backups, `transcript.jsonl`, `settings.json`, `vapid-key.pem`, `bridge-auth.json`, the token and limits caches, `server.lock`, its logs and the attachments) are written readable by the owner's Mac account alone. Each start narrows the same files an older board left readable by other accounts. `run.config.json` and the install and update records are not among them. These changes take effect when the board restarts (`facilitator restart`).

## Owner routing

Two agents share one board. Every box carries an owner tag: `facilitator` (discussion about this tool, served by this repo's agent) or a project lane such as `example` (the project under discussion, served by its own agent). `/wait?owner=...` claims only that owner's boxes, and each owner has its own busy slot and listener-presence tracking, so the two agents never block or steal from each other. An ownerless `/wait` defaults to facilitator. The server always registers the `facilitator` owner, so that default answers on a board whose `lanes` list is empty, but nothing is drawn for it until a card or a project gives it a tab: a fresh install's `run.config.example.json` has `"lanes": []` and `"navigator_lanes": []`, and no board begins with a lane nobody made. A lane is added to `run.config.json` by hand as `{"owner": "myproject", "tmux": "<tmux session>", "dir": "~/projects/myproject", "instruction": "<what to type to attach its agent>", "prompt": "<what a new agent session starts with>"}`: `owner` is required, `tmux` and `instruction` are what `facilitator run --attach` uses, `dir` and `prompt` are what `--spawn` uses, and `dir` is also the folder the board shows for that lane. A project added from the home page needs no lane entry. Nothing rewrites an existing `run.config.json`, so a board that has lanes keeps them. Two meta sections sit on top, tool-meta first, each with its own plus button; user-created boxes inherit the section's owner; the writing indicator and the offline banner name the agent. Every meta box carries the owner's remove cross, any standing card the seed placed included (box `0` for the tool lane, for instance); a lane with its standing box removed just works from its remaining boxes, and notes that would have gone there go to an open box or the project docs. The two loops, side by side:

    curl --max-time 60 -sS "http://127.0.0.1:$PORT/wait?owner=facilitator&timeout=50&agent=claude"
    curl --max-time 60 -sS "http://127.0.0.1:$PORT/wait?owner=example&timeout=50&agent=claude"

Each lane confirms its own claims against its own owner: `POST /ack?owner=facilitator&token=...` and `POST /ack?owner=example&token=...`. A token belongs to one lane's claim and is refused (409) anywhere else.

## Browsing and selecting cards

The card on screen is either browsed or selected, on the Mac board and on the phone page alike. The arrow keys, a swipe on the phone, a click or tap on another project's tab, opening the board and opening the app only browse: the card shows level with the board's surface, with no shadow, and nothing is marked read. Selecting is Enter, or a click or tap on the card or on its ticket, and a selected card wears its drop shadow. Escape lets go of the card (while the caret is in the reply box, the first Escape takes the caret out and the next lets go), and so does a click on empty board space on the Mac, or a click on the open project's tab on the Mac or choosing the open project in the phone's project list. The card stays on screen, now browsed. The phone has no empty board space, so Escape on a paired keyboard and choosing the open project in its project list are its two ways. The ticket of the card on screen is always lifted with the board's raised shadow, browsed or selected, so the list shows where you are (on the phone the ticket box above the card shows the same, and a paired keyboard can open the box and walk the list, see the card list keys below); the ticket is not made bolder, because a card with unread replies keeps its darker title as the only unread mark. Selecting a card reads it, and so does clicking or tapping into it or typing in it; browsing never reads. A reply that lands on the selected card is read at once while the board's window is in front, meaning the page is visible and has focus. While the window is behind another app, the reply stays unread until the window is back in front and the card is used as usual. When the card on screen is closed or deferred, the card below it in the Doing list shows next, browsed, or the one above when it was the last, or none. The typed page `page.html` keeps its own card handling and is unchanged. `tests/browse-and-read.test.cjs` and `tests/phone-browse-and-read.test.cjs` cover this.

Two keys move the card on screen on the Mac board and on the phone page, with the caret in a typing box or not. Control + Enter does what double Enter does: with words in the box it sends them as Enter does and then shows the card that has waited longest on the reader, and with an empty box, or with no box focused, it only makes that move. The card lands selected, as double Enter lands it, and a send the board refuses leaves you where you are, as it does for double Enter. Command + Enter stays a plain send that does not move, and Shift + Enter still makes a new line. Control + R shows a random card from the list on screen whose ticket is neither green nor grey (queued, a message waiting for the agent to pick it up), browsed as the arrow keys leave it. It never picks the card already on screen or a standing box, nothing happens when no card qualifies, and the key is not handed on to the browser. In the small card Control + Enter sends and then moves the large card, and Control + R is not answered. `tests/control-enter-and-random-browser.test.cjs` covers both keys. Option + Enter is not a key of the board: in the large card, the small card, the chat thread, a card's title, the phone's typing box and the typed page's reply line, new card line and titles it sends nothing, saves nothing and moves nothing, and the page leaves the key uncancelled, so the box does what it does with Option + Enter by default (a new line in a plain text box). Chords that carry Option with Control or Command are treated the same. `tests/option-enter-browser.test.cjs` covers it beside the other Enter keys.

On the Mac page and its narrow phone frame, Chrome shortcuts that reach the page are canceled for Save Page, Print (including the system print dialog), Stop, Find next/previous and use-selection, zoom, history back/forward, developer tools (including Command + Option + U for View Source), caret browsing, new/incognito windows, new/restored tabs (Command + T and Command + Shift + T), New Tab Group (Command + Control + P), History, Downloads, Bookmark Manager, clear browsing data, Chrome settings and Help. ## The reply chime

The Mac board rings one soft two-note bell when a reply lands: a card turns to the reader's turn because an agent answered, the same event the phone is pushed for. The page sees it as a card's `turnTs` moving between two readings of `/state`, so a card already waiting when the page opens never rings. The sound is made with the Web Audio API and no sound file: a C5 then a G5, pure sine, a soft 45 ms start, 0.91 s in all, at 60% volume (`chimeBellRoundA` in `index.html`). The first reply rings at once and any reply in the next two minutes is silent, so a cluster of replies gives one chime. The two minutes run from the last chime, and a chime that could not play does not start them. While the board's window is in front (visible and focused), a reply on the project tab being shown is silent and a reply on any other project rings under the same two minute rule; with the window behind or hidden, or with home open, every project rings. Chrome plays sound only after a click or key press, so the page wakes its audio on the first one, and a chime that finds the audio asleep is skipped, never held for later. Two windows of one browser share the two minutes through `chimelast` in the browser's storage, so they do not both ring.

The speaker at the right end of the bar, left of the squid, mutes it. It is a mark in the sub ink in a 32px glass circle like the squid's (see "The Mac board's top bar"), drawn in a 24 box with round line ends and the house icon's line width, reaching across its box as far as the house at the other end of the bar does: a speaker with two curved sound waves while the chime is on, and the same speaker with a slash across it, a clear gap round the slash, when it is off. A click flips it, and it carries a title, an `aria-label` and `aria-pressed`. The chime starts on. The choice is kept with the board's settings as `chimemuted` (`1` when muted), in `settings.json` like `bgcolor`, so every window on the board follows it, another open window within a reading. Chrome slows the timers of a window left hidden for more than five minutes, so a chime for that window can come up to about a minute late. There are no Mac banners, and the phone is unchanged. `tests/reply-chime-browser.test.cjs` covers it.

## Seeding a board

A first-ever start (no `state.json`) reads `seed.json` beside the server: the board title plus opening boxes. `seed.json` is gitignored because real discussion content is private and never ships in this repo. `./install.sh` copies `seed.example.json` to `seed.json` only when `seed.json` is missing, and the example holds a title and an empty `items` list, so a new install starts with no card, no `facilitator` tab and no example project, and opens on the home page (see "The home page"), where the first project is added. Nothing rewrites an existing `seed.json`. To start a board with cards, put them in `seed.json` before the first start: each item in `items` is `{"id": "1.1", "bucket": "must", "owner": "myproject", "title": "Fix the login timeout", "context": "the card's first reply"}`, where `id`, `bucket` (the section it stands in, such as `meta`, `must`, `could` or `later`) and `title` are required, `owner` is the lane the card belongs to and defaults to `facilitator`, and `context` is optional. The file is read once, so a board that already has a `state.json` ignores a change to it.

## Bringing everything up

`facilitator run` starts the server if the board is not up, opens the chromeless app window and, on a checkout with a phone password, leaves the phone bridge on (see below); it never touches tmux by default. It prints `Board up on http://127.0.0.1:<port>` and `Facilitator is live!` and nothing else, whatever the lanes are doing, except the one line below when the phone link cannot be turned on. The board listens on a pair of ports, the `port` in `run.config.json` and the one above it for the phone, and stays on that pair until something else holds it. A board already answering there is this board unless its `/state` names another folder (another checkout's board counts as something else). When something else holds either port (a bind of the server's own shape fails on it), run moves the board to the next free pair above, stepping by two and skipping any pair with a port a Tailscale Serve rule points at, writes the new port into `run.config.json` (only that value changes in the file, every other key and the file's own spacing kept), starts the board there and prints one line before the usual two: `Board moved to port <new>: something else is using <old> or <old + 1>. It stays on <new>, and run.config.json now says so.` The board then stays on the new pair, even once the old one is free again, until the new pair is taken too. When the phone link was on, run points it at the new pair's phone port with the same checks `facilitator bridge on` makes, and the line ends `The phone link points there too.`; any other Serve rule is left alone. A link that cannot be moved then (Tailscale not connected, say) gets one more line saying so, and the config keeps the old port as `moved_from`, so `facilitator bridge on` moves it later and `facilitator bridge off` can still take it away. When nothing answers on the configured port but this folder's board is running on another pair (the config changed under it), run starts nothing, writes that port into the config and says so in one line. After a move the Chrome app window opens at the new address; a window still on the old one shows the unreachable banner, the Mac app installed from the old address has to be installed again from the new one, and the board's settings come along (see "The board's settings"). If `app_url` in the config names the old port, the move line says so. It says nothing about the window unless the window could not be opened, which is one plain line. The window opens in full screen when `run.config.json` says `"app_fullscreen": true`, which a new install's file does (`run.config.example.json`): the launch is then `open -na "Google Chrome" --args --app=<url> --start-fullscreen`, and Chrome describes that flag as starting in full screen as if F11 had been pressed, which on a Mac is the system's full screen, with its own Space and no menu bar or Dock until the pointer goes to the top. A `run.config.json` without the key, or with any other value, launches exactly as before (`--app=<url>` alone), and nothing rewrites an existing file, so an install keeps the window it has. `--dry-run` says "full-screen" in its window line when the key is set. The flag is read by a Chrome process that is starting. `open -n` always starts a new one, but when Chrome is already running on the same profile that new process hands the address to the running Chrome and exits, and the running Chrome may open the window at the size it last had without applying the flag; press Control + Command + F once there. `tests/cli-quiet.test.cjs` covers the launch and the dry-run line. `--attach` types the attach instruction into the existing tmux sessions named in `run.config.json` (machine-local and gitignored, since lanes name real directories; a new install has none, and "Owner routing" gives the keys of one); `--spawn` additionally creates new agent sessions where none is reachable; each adds one line per lane it acts on, saying what happened, and only when given. `--dry-run` keeps the longer account of what a run would do, with the attach instruction for each lane that has no listener. A `run.config.json` that is empty, is not JSON, or lacks what a command needs is one plain line naming the file and what is wrong, for every command that reads it. Once the board answers (started now, already running, or moved), a checkout with a phone password (`facilitator password set`) has the phone bridge left on through the same code and checks as `facilitator bridge on`: Tailscale connected, HTTPS certificates on for the tailnet, no other service on the HTTPS root, no Funnel on it and no old unguarded rule. It prints no QR code and no line when the link comes up, and changes nothing when it was already on and pointing at this board. When it cannot come up, the board is up all the same, run still succeeds, and one line follows the two above: `The phone link is off (<why>). Run facilitator bridge on when that is fixed.` After a move the link is pointed at the new pair first, as above, so a move whose link could not be pointed gets that line and no second one. A checkout with no password is left alone: run asks Tailscale nothing and says nothing about the bridge. `--dry-run` adds `bridge: would leave the phone link on, as facilitator bridge on does; nothing changes when it already is` when a password is set. `facilitator restart` stops and restarts only the server: it signals the one process holding the listening socket on the configured port, with SIGTERM and never SIGKILL, after reading that process back as this folder's `server.py` twice, once when it is found and once in the moment before the signal. What is read is the kernel's own answer about it: start time, executable and argument vector, which must be exactly our `server.py` under an interpreter this board uses, so a pid that has been released and reused, or a process that has become something else, is refused rather than killed. It polls until the port is actually free before starting the replacement (an unreadable port is never treated as a free one), then waits for the new server to answer AND for the one listener to be that exact child before saying anything went well; a port taken over by something else is refused and that process is never signalled. It then says `Board restarted.` (`Board started.` when nothing was running) and nothing more. It leaves the browser alone: a Chrome tab or chromeless app window already showing the board is kept as it is and a second line, `Reload the board (command + R).`, asks for the reload, a new app window is opened only when Chrome is certainly showing the board nowhere, and when Chrome cannot be asked nothing is opened and nothing is said. A restart that has stopped the old server but cannot start the new one says so, that the board is down now, and that `facilitator run` starts it. It touches no lane, no tmux session and no bridge, and never moves the board: it restarts on the configured port, and when this folder's board is running on a port the config does not name (`server.lock` says which) it says so, names both ports, and starts nothing, since `facilitator run` is what brings the two together. `--dry-run` prints the plan and changes nothing. `facilitator stop` ends the server the same way and closes the board's own window, saying `Board stopped.` (`Board was not running.` when nothing was), and, with a phone password, takes the phone link off last; the rules for what it signals, closes and takes off are under "Restarts". `facilitator status` prints a one-line board summary. Restart, status, update, uninstall and the bridge all read the port from `run.config.json`, so they follow a move.

`facilitator update` brings a checkout up to date so nobody has to run git by hand. It stops, changing nothing, when the checkout has uncommitted changes, is not on a branch, or has no upstream; otherwise it runs `git pull --ff-only` for that one branch on its own remote, which only moves forward and never merges, rebases or rewrites. Once the pull has landed it starts the pulled code's own `_update-steps` as a new process, so a routine pushed later runs on the same update that brings it. That process first checks that uv is 0.9.0 or newer (an older one stops the update with one line saying to upgrade it) and rebuilds the `.venv` on Python 3.14 when it is missing, broken or on another Python, saying so in one line, stopping a board that runs on the old `.venv` before that and starting it again at the end; then it syncs the `.venv` to `requirements.txt` with uv and no questions, then runs each numbered step in the `updates` folder (`NNNN-what-it-does.sh` or `.py`; see `updates/README.md`) that has not run in this checkout, in name order. The run prints three sections, 1. Checkout, 2. Update steps and 3. Board; the pull and the `.venv` sync have no section and print nothing unless one fails, in which case its error and what to do print as before, or the `.venv` has to be rebuilt, which is said in one line. A step that exits 0 is written to the gitignored `.facilitator-updates.json`; a step that fails stops the update by name, is not recorded, and runs again next time. The board is restarted through the same safe `facilitator restart` only when something was pulled and it is running; a board that is not running is not started, except one the `.venv` rebuild stopped, which is started again whether or not anything was pulled. The run ends with the old and new version and a reminder to reload the board and reopen the phone app, or says it is already up to date when nothing was pulled, in which case pending steps still run and nothing is restarted. The restart's own result shows once, as `Board restarted.`, with the reload line when Chrome has the board open.

The board installs as a Chrome app once per Mac, which is what gives it its own icon in the dock. Open the board's address (`http://127.0.0.1:<port>`, the one `facilitator run` prints) in an ordinary Chrome tab, not the chromeless window, and press `Install app` in the bar at the top of the page, then Install in the box Chrome puts up; Chrome's own install control at the right of the address bar does the same thing. The control on the page stands there only while Chrome is offering an install, so it is not there before the board qualifies, inside the installed app, or once the install is done. Chrome writes a small Mac app named for the board's manifest into `~/Applications/Chrome Apps.localized`, carrying the board's mark. `facilitator run` keeps opening the chromeless window either way; the installed app is opened from the dock or Launchpad like any other app, and moving it to the bin removes it with no other change. The install is per Chrome profile, and the phone page's own app at `/m` is a separate one that this leaves alone. The installed app belongs to the address it was installed from, so after `facilitator run` has moved the board to another port it opens the old address until it is installed again from the new one.

## The phone page and the bridge

The Mac board's portrait view is this same `/m` document in a retained, full-window same-origin frame, managed by `mac-phone-view.js`. There is no separate imitation phone layout. The existing thresholds remain: enter when height exceeds 1.26 times width, or width is below 54 percent of the left and middle board's design width; stay until height falls to 1.14 times width and width reaches 46 percent. Height-only resizes check this boundary but keep the usual landscape geometry freeze. The wide and two-pane board fitting is unchanged.

A resize carries the project, card, browsing/Home state, ticket section, every card's unsent text and its caret between the live pages. Each page keeps its drawers and other controls mounted. The handoff waits while text composition, a title or new project edit, an attachment upload or an unresolved send needs its original controls; a short notice explains this, and switching follows automatically when the work settles. Failed phone attachments or sends keep their retry/remove controls accessible. Completed phone attachments become the same upload links the Mac composer already uses. Resizing back cancels a pending handoff. No draft is put in a URL or sent to the server by a resize. A hidden page cannot mark replies read.

The Mac document stays mounted under the phone view, keeping file edits, Spotify and other Mac panels alive. In the embedded phone's settings, the Mac section has the reply-chime switch and Open Mac board, which reveals those controls at the current window size; Back to phone view returns to the same phone document. The Mac chime follows the phone's current project and Home state, and the Mac browser-shortcut guard also runs in the frame. This local view has no phone logout or push switch and does not register the phone service worker. Direct `/m` visits, including the iPhone PWA, retain their usual appearance, keyboard behavior, sign-in, worker and notifications. Loopback `/m` needs no password. Installing this change needs a server restart for the new static route and narrow framing exception, then a reload of the Mac window. No restart is performed by the page.

`GET /m` is the board for a phone: one card filling the screen from under the status bar down to a row of four glass buttons along the bottom, and the card list (doing, deferred, done) above the card, in a shortened copy of the Mac board's ticket box. Pulling the card from the left edge, or tapping the ticket circle, sends the card down 55 percent of the screen's height while the box slides in from the left into the space above it, the two together and following the finger. With the list out the box takes 90 percent of the space the drop opens each way (`--list-share`), the card's resting width across and the drop down, and stands in the middle of that space with paper all round it. It shows the same rows the Mac board does, scrolls inside itself, paints no panel of its own, and lies under the card. It is seen only through a window (`#tikwin`) whose foot is the card's top edge: the window goes down with the card and the box inside goes up by as much, so the box holds still, the card going down uncovers it, and no part of it shows beside the card or under it at any point of the slide. The card, the box and the window are driven by one fraction, `--list-v`, that the script writes on all three, and they move by transform alone: no layout is done in a frame and no script runs a frame loop, and a swipe let go past the middle finishes the run, while one let go before it, or the reverse swipe, undoes both together. The page does not draw back for the list and casts no shade over it. A tap on a ticket switches the card and leaves the list out; a tap on the card that shows, the reverse swipe, the ticket circle again or Escape shuts it, and while it is out the card takes no touch of its own. The size of the drop is written on the page in pixels as `--list-drop` and again only when the screen's height changes, so a turn of the phone leaves no stale offset. On a paired keyboard, Control + Shift + comma opens and shuts the list, up and down walk it and Control + Shift + left and right step the cards; the settings drawer has no key; see "Browsing and selecting cards". The row sits in the band iOS 26 gives a paired keyboard's bar (48px tall, 10px above the bottom edge, 16px in from each side, 20px on the widest phones): a ticket circle that opens the card list, the project oval, which names the open project (or Home) and opens the project list above the row on a tap, a plus oval that makes a new card, and a squid circle that opens the settings drawer. The squid is the same logo png as on the Mac bar, cut to the squid's own bounds, 30 units tall and centred in the circle, so it keeps its colours when the button is pressed. The row stands on a layer of its own above the card (`#dockbed`), and the card slides under it: its top edge fades out as the Mac card's does, and the paper is whole from the buttons' tops down, so no word of the card shows beside or between the buttons. At rest the card's foot stands on that edge. As soon as the list starts to come out a second sheet rises over 0.165 seconds, 16 units of whole paper over the buttons' tops with the 22-unit fade above that, so for the whole slide and with the list out the white band and the start of its fade stand higher; it settles back over the last 0.165 seconds of the card's run home. The bed casts no shadow of its own (the soft shadow it used to lay along its edge read as a dark band over the card's lines as the card went down); each button keeps the glass's own shadow. Each button grows a little under a finger and settles back when it lifts; a finger held on the oval does no more than a tap, and a press still showing when the app is put away is dropped, so no button comes back grown. The buttons and the project list wear the quick note's glass, and their top edge is one line, the same grey ring that runs round their other sides. The project list holds Home first, then the projects in the board's order; holding a project row and dragging it reorders the tabs. While the project list is open the page and the row behind it are dimmed a little, in the settings' shade at a lighter weight, and the dim fades away when the list closes: a tap outside it, a choice in it, or Escape. The row fades out when a typing box is touched or focused and lies under the paired keyboard's bar, or, with the on-screen keyboard, is moved while invisible into the band of the keyboard's toolbar, and comes back once the keyboard or bar has gone. The card does what the desktop card does: the full reply, the sent messages, older replies (the arrows in the card's top bar), a composer that sends, a plus that attaches files through `/upload` (below), the defer chip and the close cross. Nothing else is on the phone.

At rest the page already has the size and spacing it used to have only while a drawer was fully out: its elements are laid out at 98.5 percent of their full size, with the page standing in from each edge by 0.75 percent of the screen's own width at the sides and of its height at the top and bottom, so the same elements sit further apart. This is real layout and not a transform, so type is drawn at its own size and stays crisp. `--sink` in `m.html` (.015) is what the page gives up on each axis and `--rest` is one minus that; `--u` is one page pixel, `1px` times `--rest` on the page and the project list and a plain `1px` everywhere else, and every length on the page is its full length in `--u`. Nothing is counted in the pixels of one phone: the step in from the edges is a share of the screen (`--rest-gap`), the safe areas, the keyboard's lift and the row's band are measured from the real screen or scaled from it, and the picture is the same on every iPhone. The settings drawer coming out draws the page back by the same step again, `--page-scale`, a transform from the page's middle that the script writes as `1 - PAGE_SINK` times how far the drawer is out (it reads `PAGE_SINK` from `--sink`) and that is empty, so the identity, at rest. The card list does not: it moves the card down and leaves the page its size. The settings drawer and what is in it, the quick note, the unreachable-board banner and screen, the startup curtain and the Omni Card's glint keep their full size, as do shadows, hairlines and gradients. Safari lays a line out at a whole number of pixels, so a line of the card's prose stands about 0.4 pixel taller at rest than the same line scaled would, and a long reply runs a few points longer; the boxes themselves match to within a point. `tests/phone-rest-geometry.cjs` holds the rest geometry (the step in from each edge and the row's foot, side and band) that the phone tests measure against.

A file picked with the plus, pasted or dropped (a photo, video, recording, PDF or Word file, up to 100 MiB) goes into a tray over the typing row and starts uploading at once, one file at a time. Each file is a square with its picture or its kind, a ring showing how much has gone, and a cross to take it out; no words stand under the tray, so the squares alone show the state. The words stay in the row, and when the message is sent the files go with it as `/uploads/...` lines ahead of the words, pictures on one line so they show as the card's grid. A send pressed while a file is still uploading waits in the row and goes when the upload finishes. An upload that does not get through is tried again on its own, up to five times and at once when the app is back on screen or back online, then waits with a red round mark for a tap. Each upload carries an operation id and the board remembers what it stored under it until it restarts, so a try whose answer was lost is answered with the file already stored rather than sent again. A file the board refuses wears the same red mark, with no words, and is not tried again: its first bytes are not the kind its name says (a page renamed `.png`), it is an SVG that carries script, or it is empty or too large. The board waits for any upload, the desktop's too, as long as bytes keep coming: it gives up after a minute with nothing arriving, or an hour in all.

After a picker closes, the plus is dimmed and holds taps until the phone hands the page its focus back (or the page is shown again), because the phone drops a file-input tap for up to two seconds while it takes the picker down. The page adds no wait of its own on top: the plus is back the moment the focus is, and only when nothing hands it back does a clock end the hold, at 2.5 seconds after the close. A close within a quarter second of the open is the previous picker's and is ignored.

The phone builds a card only for the card on show and the cards around it: the next and the previous in the order a swipe or a card key walks, and the next and the previous in the order the card list shows, built as soon as the switch has been drawn. A card two places or fewer from the one on show, in either order, stays built, so going back and forth among a few cards builds and takes down nothing; a card farther away is taken down and built again when it comes near. This is what keeps the keyboard rising and falling, and the card list or the settings being pulled, from restyling every card of a board of hundreds. On the iOS Simulator with a board of 760 cards the page holds three or four cards instead of 760, and one keyboard open and close, which kept about 46 MB, keeps about 1.4 MB. That 1.4 MB is the same on a board of 60 cards (1.8 MB), so it does not grow with the board, and it was there before (the old page on 60 cards kept 5 MB). A card taken down hands its typed words, its caret and the scroll of its reply to a shelf in the page, and is built again as it was left (the scroll only while the reply is the same one). A card is not taken down while it holds the caret or its title is being typed, has files in its tray or a send held for them, has a send the board has not settled, is being made, or has an older reply being read. Building and taking down wait for a pull of the list or the settings, or a swipe, to end, and for typing to pause. A card taken down loses its undo history and whether its sent messages were folded open. `reachCards`, `nearbyCards`, `ensureCard` and `dropCard` in `m.html` decide all of this, and `tests/phone-nearby-cards.test.cjs` checks the number built, the shelf and the held send.

While the caret is in a card's typing box, the plus steps aside and the box takes its place, whichever keyboard is in use: the soft keyboard, a paired keyboard with the thin toolbar the phone still shows, or a paired keyboard with nothing on screen at all. The plus fades to nothing and shrinks to 70 percent, stops taking taps, and the text slides left over the place it stood, all in 0.22 seconds on the keyboard's own curve. The motion starts on the same frame the phone reports any lost height, the frame of the card's rise above the keyboard or the toolbar, and a tenth of a second after the focus when the phone reports none. Only once that motion has ended and any rise has landed is the row made wider for real (the box keeps the room and the plus leaves the row's layout), because changing a focused box's layout on the frame it is tapped makes the phone take the keyboard down; the caret is held invisible from the tap until just after that switch. When the caret leaves the box, the row plays back the same way over the same 0.22 seconds and the plus takes taps again at once. A keyboard that goes away while the caret stays in the box leaves the plus hidden. While the caret is in the box, the plus is reached by taking the caret out: the check on the keyboard's own bar, the pull that opens the card list or the settings, the card list's key, the home button, or Escape on a paired keyboard. The tray over the row and the send square do not move, and the desktop board and the typed page are unchanged.

The phone reads the board through `GET /m/state`, naming the revision it holds, so a poll that finds nothing new costs a few hundred bytes; it refreshes every 1.2 seconds while on screen, with a backoff on failure. While the app is in use nothing on screen changes when the board stops answering: no bar across the top, and no screen over the card. The phone shows a plain white screen with one line, "Is the Facilitator server down?", and a small line drawing of a face with crossed-out eyes, only when the app is being opened and the board does not answer. The app is being opened when the page loads (a fresh launch, a reload, or the phone restarting the page) and each time it comes back on screen after being in the background; the first read after that decides, with its normal 8 second wait, and if it is not answered the screen comes up at once. A touch, a tap, a key press or typing before that first read is answered counts as the app being in use, and the screen does not come up for that opening. Once a read after the opening is answered the app is in use, and a board that stops answering never brings the screen up, however long it lasts. The screen goes away on its own when a read gets through, leaving the open card and any unsent words as they were, and a refusal (401 or 403) counts as the board answering, so it never brings the screen up. When something has changed, a phone holding a reading this server run sent names it (`delta`) and gets only the cards that differ from that reading, with where new cards go and which cards went; the server remembers its last 32 readings for this, and a phone holding one it has forgotten, or one from before a restart, gets the whole board once. Every answer of 256 bytes or more is gzip compressed when the phone accepts gzip, which Safari always does. On a test board of about 700 cards, about 800 KB whole, a change now costs a kilobyte or two on the wire, and a whole board (the first open, or the first change after a restart) about a quarter of its size. A read has 8 seconds for its answer to start; after that, a download that keeps arriving is waited for however slow it is, and only one that brings nothing for 8 seconds is given up and tried again. A phone page opened before this change keeps working against it and reads whole boards, now compressed; this page against an older server reads whole boards as before. Every send and every new card from the phone carries an operation id, and the server keeps the result beside the effect: a retry after a lost reply is answered from the receipt and never lands twice. A message is faded, with no word under it, until the board has saved it (what would be lost if the app were closed now); then it is at full ink and says "Delivered", and once an agent has picked it up it says "Read". The Mac board draws the same three looks, fading a message from the press of send until the board answers. Once the card's newest reply is newer than a message, the word under it fades out over about 0.4 s (its strength only) and stays gone, on the phone and on the Mac board; the room the word stood in is kept, so the reply and everything below it do not move. A page drawn with the reply already there (a reload, opening a card, scrolling to it) shows no "Read" and no fade, and a message sent after the newest reply keeps its "Delivered" and "Read" until a reply comes after it. A message that fails to send stays in the sent messages and never carries a sentence. One the board could not be reached for is tried again on its own, across a lock and a reopen, for half a day, and while that goes on its row shows the upload tray's turning ring. After that nothing more is sent for it and the row wears a red round mark at its right edge, holding a circular retry arrow, with a small cross beside it. Readings keep asking the board whether it landed, and the board's receipt settles it either way, as Delivered or as failed. A message the board refuses (400, 409 or 413) wears the same mark at once, shows no reason, and its arrow does nothing. The arrow sends again under the same operation id, so a message the board already has is answered from its receipt and never lands twice, and it is safe whether or not the board can be reached. The cross takes the message back and puts its words in the typing bar. A refused message gives its words back at once, as does one the board has no receipt of, which proves it never landed only while that still holds (about a day and a half). One whose fate the phone does not know first asks the board for its receipt: landed, and the row becomes Delivered with nothing taken back; not landed, and the words go back; the board out of reach, and the cross does nothing until it can be asked. On the Mac board every send carries an operation id and the board keeps the receipt, the same as the phone; a send with no answer after 10 seconds shows the same mark and cross in the sent messages, and the arrow and the cross work as they do on the phone. At most fifty unconfirmed messages are kept; past that a send is held with its words left in the composer until room is made. The plus on the bottom row makes one card per press: a second press while the first is still being made is the same press.

`facilitator bridge` toggles the phone bridge, `facilitator bridge on` enables it, and `facilitator bridge off` disables it. On and off are idempotent. Enabling prints a QR code for the phone page and returns while Tailscale keeps the bridge active; it stays active until an `off` command or `facilitator stop` removes it. On a checkout with a phone password, `facilitator run` and `facilitator stop` make these same changes themselves, through the same code and checks (see "Bringing everything up" and "Restarts"), so a board that is up has its link on and a board that was stopped has it off, and nothing is printed when the checks pass; the commands here stay for switching the link by hand and for the QR code, which run never prints. `facilitator restart` leaves the link as it is. The server listens on two loopback sockets: the board's port (the `port` in `run.config.json`, 8877 unless the board has moved) for the local desktop and agents, and the one above it (8878 beside 8877) for the phone bridge. It binds both before it reads anything, then takes `server.lock` beside `state.json` and holds it for as long as it runs, so a second server from the same folder, on any pair, stops before it reads `state.json`; the file names the running server's pid and port. The HTTPS Serve root handler proxies only to the phone port, where the server requires a password-backed session on every state, command, attachment and desktop route. A phone opened from the QR in Safari sees an install card first; a Home Screen app opens at the password box. Sign-in persists across reopens and server restarts until the turn off button at the bottom of the settings drawer, answered Log Out, or `facilitator password set` invalidates it. The cookie is Secure, HttpOnly and SameSite Lax, so it also arrives when a link from another site opens the phone page; every write is still refused unless it comes from the bridge's own origin, and a GET or HEAD that another site sets off (`Sec-Fetch-Site: cross-site`) is refused with 403 and logged for every route except the page opens `/m` and `/`, so a link or a notification can open the phone page but cannot claim or fold messages, open the folder dialog or trigger any other route. A request with no `Sec-Fetch-Site` header is treated as before. A phone signed in under the older Strict cookie switches over without signing in again: each time the signed-in phone page is opened, the same session is sent back once with the Lax attributes, and the polls after it send nothing. The server stores only a password hash and session hashes in the gitignored `bridge-auth.json`, separate from board state. Signing out also stops push delivery for that session. The board's own local socket keeps the agent protocol unchanged. An older Serve rule targeting the board's own port (8877 on an older install) must be removed with `facilitator bridge off` before starting this version: server startup refuses to bind that port while that rule exists, so it cannot remain an unguarded remote path. Then set the password if needed, restart, and run `facilitator bridge on`. The off command removes only its root handler and leaves unrelated Serve paths, ports, Funnel routes, foreground sessions, and named Services alone. A conflicting root, Funnel on the same HTTPS endpoint, or another configuration that exposes this board is reported without changing anything. Tailscale only issues certificates once HTTPS certificates are switched on for the tailnet, a one time change under DNS in the Tailscale admin console; with that off the command says so and stops. `--dry-run` reads the live state and prints the one change it would make.

Notifications: add the page to the phone's home screen (on an iPhone push only works from there), open it, pull in the settings drawer from the right edge, open its Notifications section and turn the Notifications switch on. The switch is the same on and off pill as Format text while typing. The phone saves your on or off choice. The switch is on only when that choice is on, permission is granted and the board has accepted this phone's subscription. On open, return and opening settings, an on choice restores a missing subscription or sends an existing one to the board again. While that is pending, the switch says "Restoring notifications..."; if it fails or needs a tap, "Restore notifications" tries again. "Turn notifications off" cancels an on choice even during repair. Turning it off saves off, removes the subscription from the board (`POST /push/unsubscribe`) and unsubscribes the phone independently; a failed removal is retried on return. Sign-out cancels repairs, clears the saved choice and removes the subscription. A failed save keeps the phone's subscription for retry. An older phone with no saved choice keeps an existing allowed subscription; if that subscription is already gone, turn notifications on once to save the choice. While `facilitator bridge` is up, the server sends one push each time a card turns to your turn: a plain reply with no live working flag, or a working flag dropped or expired while a reply waited. It checks that Tailscale is connected and that the active HTTPS Serve proxy points to this board before each send; a turn while the bridge is down does not push later, and subscriptions stay saved for the next live turn. The phone app may be closed or in the background. Progress notes never push. Each push carries that event's card id and title in an encrypted `aes128gcm` payload, so delayed events retain their own card. Every received push tries to show that title at once without asking the Mac first, even while the app is visible; a missing or empty title shows "facilitator". The server still checks the sign-in before each send, but a title already on its way at sign-out can still appear. Reopen the phone app to load worker `facilitator-m-11` and the new page after these files are installed; this change needs no server restart. The signing key pair is `vapid-key.pem` beside `state.json`, made by `openssl` on first need and gitignored; subscriptions live in `state.json` under `push_subs`.
