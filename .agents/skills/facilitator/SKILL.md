# Facilitator onboarding

`onboard` joins the board from this agent conversation. The usual invocation is `/facilitator onboard` in Claude Code or `$facilitator onboard` in Codex. The optional `--board NAME` selects a lane by ID or project name; `--path DIR` selects by project directory. Without either, use the directory where **this agent session** was started. Do not use the owner's separate terminal directory.

From that session directory, run `python3 "$HOME/.agents/skills/facilitator/scripts/onboard.py" inspect` for either host. Set the tool's working directory to the session's starting directory if it has since changed. Pass the user's `--board` or `--path` option unchanged. Its JSON result names the lane, port, and absolute `runbook` path. Read that runbook for the shared board protocol and operating rules; it is the maintained source of those rules. This skill only supplies the joining procedure.

- `ready`: join the named lane now. Keep listening in **this conversation**, including when the queue is empty. Do not launch a separate agent, daemon, hook, server, or another listener to do it.
- `down`, `different_board`, or `different_server`: report the board condition. Do not start or replace the server.
- `ambiguous`, `project_unknown`, or `path_missing`: ask which project or path to use. Do not guess a lane.
- `listener_present` or `claim_held`: avoid a second listener. If this conversation already holds the claim, finish it; otherwise report the occupied lane and let the existing listener work.
- `link_down` (only on a server, see below): the board on the owner's Mac cannot be reached now (the Mac asleep, Tailscale or the board down). Report it and do not start anything; the connection comes back by itself.
- `key_refused` (only on a server): the board does not know this server's key any more. Report that the owner has to pair this server again with `facilitator remote pair`.

For each listen cycle, call `python3 "$HOME/.agents/skills/facilitator/scripts/onboard.py" wait --owner OWNER --agent NAME`, with `NAME` identifying this host. The helper waits up to 7 minutes (420 seconds) in one request, confirms a received claim immediately through `/ack`, and uses a 430-second client deadline; `--timeout SECONDS` (1 to 540) sets another length. It makes one foreground listen cycle, and the host's default command limit is shorter than the listen, so run it as follows. In Claude Code, call Bash with the tool `timeout` set to 600000 (10 minutes, the most Claude Code allows by default); at the default 2 minutes the command would be cut off before the listen ends. In Codex, the command hands back a still-running session after a short wait: wait on that same session (`write_stdin` with empty `chars` and a long `yield_time_ms`) until the command ends and prints its result, and do not start another listen meanwhile. If any other tool yields a still-running session, resume that session instead of starting another. On `idle`, check worker results and card heartbeats, then listen again. On connection failure, report the loss of the board instead of starting it. Never answer a claim that the helper reports as unconfirmed.

If a later wait reports an occupied or unavailable board, use the same handling as during inspection. On `ack_failed` or `protocol_error`, stop and report the failure; do not answer an unconfirmed card. On a server, a wait that answers `link_down` has kept trying through its whole listen while the board could not be reached: keep working on what you hold, and listen again as after `idle`; messages sent meanwhile wait on the Mac. A wait that answers `key_refused` means this lane's key was replaced or dropped: run `inspect` again, then listen.

**On one of the owner's servers.** When `inspect` answers `"remote": true`, this conversation runs on one of the owner's own servers and the board is on the owner's Mac, reached by connecting out to it over Tailscale; the board never logs in here. `inspect` also starts this server's link to the board when it is not running, which answers the board's folder picker; that is the helper's own and not a listener of yours. The listen is the same command; it makes its calls in short pieces inside the same deadline. The runbook's curl lines still apply with two changes: put `-K` and the file named in the `curl` field in front of every curl, and write the `base` field, `http://board`, where the runbook has `http://127.0.0.1:$PORT`, for example `curl -sS -K ~/.facilitator/agents/LANE.curl "http://board/fresh?owner=LANE"`. That file holds this lane's own key and the board's address: never print it, copy it or put it, the key or the address in a reply. Only this lane's own routes answer. The `facilitator` command is not on the server: for the magic box, run `python3 "$HOME/.facilitator/skill/.agents/skills/facilitator/scripts/magic.py"` in place of `facilitator magic`, with the same words after it (`... magic.py CARD KIND ...`, `--help` for them); it sends them to the board with this lane's key, for this lane's cards. When a call fails because the board cannot be reached, try it again a minute later; the card waits.

Immediately before **every** `/reply`, including an interim or worker-completion reply, call `/fresh?owner=OWNER` as its own step and read the returned `box` and `messages` before composing. Include fresh messages when they belong to the card being answered. If `/fresh` names a different held card, handle that claim first; never use its messages to answer another card. An empty result with no held card hands over nothing. Send a complete, self-contained `/reply?box=ID` with the reply text as the request body. If work continues, set `/working?box=ID&v=1`, keep `/ping?box=ID` current, send a full interim `/reply` while the flag is live, then drop the flag with `v=0` only when that work ends. Post the final reply first, while the flag is still on, and only then turn the flag off; turning it off first hands the card to the reader at once, so it shows a stale yellow card with the old reply until the final reply lands. Progress goes out as a normal `/reply` while `/working` is on. Continue listening after each reply. Keep the runbook's delegation, reply, and permission rules in view while doing the work; no skill instruction grants permission beyond the current user and host authorization.

To show the owner a picture, a mock, a page or a website beside a card, unasked only when it truly helps them understand something (never a report or long text unless they ask for it), run `facilitator magic CARD KIND ...` (`facilitator magic --help`), or on a server the `magic.py` named above with the same words; the runbook's "The magic box" section has the kinds and the rules.

When someone asks how to install, set up or use Facilitator, read `docs/README.md` in the folder you cloned (this skill's folder is a link into it: resolve this file's real path and go up three folders), open the page it names, answer from that page and name it. Do not answer from memory.
